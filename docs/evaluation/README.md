A [Senzing model trial](https://github.com/Mokto/opengeocoding/issues/98) on the same full index and 4,188 gold cases led to the corroboration and comma-boundary fixes above. With the default model, SearchAddress passes rose from 3,656 to 3,670; with Senzing's v1.2.0 parser bundle, from 3,604 to 3,638. Neither repair comparison introduced a newly failing case or a worse failure class. Switching models after the fixes still caused 86 newly failing cases and 44 worse failure classes, so the default model remains selected. The `evaluate` binary (`src/bin/evaluate`) measures geographic correctness of the service and its index through the service's RPCs. It is for backend, data and consumer changes; it does not measure throughput. Build it with the service:

```sh
cargo build --locked --release --bin opengeocoding --bin evaluate
```

| Suite | Command | Needs |
| --- | --- | --- |
| PR (CI) | `cargo test --locked` (or `target/release/evaluate check`) | Nothing; scorer, diff gate, corpus and snapshot checks |
| Smoke | `target/release/evaluate run --suite smoke --index out --out eval-results/smoke` | Index, models |
| Pre-release | `target/release/evaluate run --suite gold --index out --out eval-results/gold` | Same |
| Address snapshots | `target/release/evaluate run --suite addresses --index out --out eval-results/addresses --compare tests/snapshots/addresses.tsv` | Same |
| Compare | `target/release/evaluate diff BASELINE CANDIDATE` | Two saved runs or snapshots |
| Re-score | `target/release/evaluate report RUN_DIR --rescore` | A saved run; lists cases whose class changed |

`run` starts `target/release/opengeocoding` (or `SERVICE_BINARY`) on the index in `--index DIR` (or `INDEX_DIR`) with no other environment than `PARSE_CACHE=0`. It sends each case `--repeat` times (default 3) and records the fastest, outside the rate limit and budget; `diff` opens with a speed section comparing those latencies in aggregate, one table each for SearchAddress, SuggestAddress (the `full` and `name` checks) and ReverseGeocode (at the case's single expected point, including same-place address alternatives, so a house where the case is one). Passing speed reports keep the headline visible and collapse the details; slowdown reports stay expanded. The speed check fails when the total, p50, p90 or p99 of any table is more than 10% slower (not part of `diff`'s exit code; CI reads the section's `<!-- speed: pass|fail|skip -->` line), and skips sides timed with different `--repeat`. Three runs of one binary on a cluster node agreed within 2% in total and 5% at each percentile, single cases only within about 30%, so single cases and the max are not gated; a laptop's totals moved by tens of percent. It rate-limits its RPCs (`--max-rps`, default 20) and stops after a request budget (`--budget`, default 20,000) when `--rpc` targets an external service; the local service it starts has neither limit unless you pass them. It counts each case's index searches from the service's `/metrics`, since cases run one at a time. For direct checks (`--no-direct` skips them) it loads the same index and its own libpostal parser, about 4 GB besides the service's. `--rpc URL` targets a running service instead, one request per case; search counts are then unavailable, and direct checks run only with `--index`. Results are checkpointed per case (`--resume`); the process is stopped on exit, including after Ctrl-C. No request is retried by the evaluator.

Each run writes `manifest.json` (a hash of the index's `meta.json`, which names its segments, consumer commit and binary hash, libpostal model and reference-data hashes, cache state and limits), `results.jsonl` (full responses, index search counts, direct-index evidence) and `report.md`. Label the backend with `--backend-label`, e.g. image digest and configuration. A code or configuration comparison requires the same built index; a data or import change is a separate experiment.

### Gold corpus

`tests/gold.jsonl` is generated by `evaluate build-gold` from the curated case list in `tests/gold.seeds.jsonl` (one line per place or construct: queries, cohort, tolerances, must-pass and known-failure labels). Expected coordinates, countries, regions and components come from Wikidata, Base Adresse Nationale, PDOK/BAG, the US Census geocoder, postcodes.io, Kartverket (© Kartverket, CC BY 4.0), swisstopo's building address register (© swisstopo) and CartoCiudad (© IGN/CNIG, CC BY 4.0), never from Nominatim or this service. Sampled cities, towns and regions in about 240 countries and territories (some written as production writes them: "Stratford, CT", or a bare unique name) were picked from GeoNames by population and production weight, sampled registry addresses from Overture, and landmarks from Wikidata items with a street address; GeoNames and Overture only chose the cases, and their expectations come from the sources above. A place in a territory with its own ISO code (Puerto Rico, Réunion, a French overseas department) accepts that code or the sovereign country's.

200 landmark cases tagged `house-coverage` (20 each in the United Kingdom, Vietnam, Thailand, South Africa, the Philippines, Malaysia, India, Egypt, Nigeria and Ireland, where the coverage audit found potential additions) were drawn in a seeded order from Wikidata items with coordinates and a street address that contains a digit, at least 8 sitelinks in the United Kingdom and 1 in India and Nigeria, where bulk-imported bank and school items dominate. The query is the address, then the containing division and the country when the address names no country. 78 cases whose address states an unambiguous leading house number require that house and number, retaining the pre-selected 1 km landmark tolerance; the rest require a street and accept a house. These tolerances measure coarse coverage, not entrance accuracy. The four excluded leading numbers are a postcode, two kilometre markers and a Thai route number. Expectations were regenerated from Wikidata, not the new source or a geocoder. A landmark may be one of the places that source lists, so these cases favour it over residential addresses. Sixteen critical failures shared by both indexes were triaged and labelled in the seeds (missing streets, ambiguous localities, consumer rejection and one conflicting Wikidata address/point); no expectation was loosened.

The `degraded` cohort (929 cases) takes registry-verified addresses and changes one thing in the query: no country, no postcode, a typo in the street or town, a wrong postcode, another town with the right postcode, a neighbouring country, the parts reversed, all capitals or lowercase, or an abbreviated street type. The expected answer stays the registry's address, re-verified by `build-gold`. Edits that leave the address consistent expect goodMatch true; contradictory ones (typos, wrong postcode, town or country) accept either goodMatch value, since whether a repaired match is "good" is not decided. Cases are tagged with their kind (`typo_street`, `wrong_country`, ...). `build-gold` looks each registry reference up once, one registry at a time in parallel, and reads Wikidata in batches of 50; the 2,894 cases took about a minute to regenerate. It covers cities in many scripts, street addresses, postcodes, regions, ambiguous names, rural places, borders, fallbacks, malformed input and no-result input. Each case records an expected country, a resolution range, an area (point and radius, or ISO 3166-2 code), relevant components, a goodMatch expectation, provenance, licence and review status. Variants share a `location` key so they are not counted as independent places. Roughly one in five locations is held out by a stable hash and reported separately; keep it out of tuning. Review status is `source-verified`; human review is pending.

Cases are scored as `pass`, `confidence_mismatch`, `too_coarse` (a fallback never passes an exact-address case), `abstain`, `too_fine`, `wrong_component`, `wrong_region`, `near_miss`, `far_miss` (>100 km), `wrong_country` or `error`. Critical classes are listed individually, flagged when goodMatch was true. For failures the evaluator queries the index directly (raw, structured, reverse, details) to hint whether the backend lacked an acceptable candidate or the consumer rejected one. SearchAddress, ResolveRegion, ListRegions and SuggestAddress are exercised.

Every case with a place, postcode or address to find, except the `degraded` cohort (repairing a damaged address is SearchAddress's job), also types its query into SuggestAddress (`full`): it passes when one of the 5 suggestions is in the expected country, of a type of the expected level (`address` for a house; `street`, or `address` when the case accepts a house; `postcode`; `country`; any place type otherwise) and within the expected radius. Where the text before the first comma is the place's English Wikidata label, `build-gold` adds a `suggest` check of that name alone (`name`): the located Wikidata items with that label and more population (P1082) are listed in `larger`, and the place must come no later than right after them (`rank`). So `Paris` must suggest Paris, France first and Paris, Texas no later than second; a name with five or more more-populous namesakes is not checked. Both are classed `pass`, `ranked_low`, `missing` or `error`, reported per cohort with every name out of population order, and add up to two RPCs per case. In one run on a world index (Overture 2026-09-23.1), `full` passed 943 of 1,947 cases (5 of 721 addresses: a complete address with its postcode and country is rarely completed) and `name` 670 of 829. Every case with a single expected place and point, including `any_of` alternatives with identical point, country, region and level, also asks ReverseGeocode at that point (for a place of a locality or finer) and ResolveRegion (for a place in a known region, at region level or finer). ReverseGeocode passes when its first result is in the expected country and, where the case lists regions, in one of them. For a locality case with a `suggest` name (its English Wikidata label), the result must also name that place among its locality and region names, compared after folding case and accents: a house or street of the next village, or of a district that has no locality under it, is `wrong_place`. Spellings that differ from the label ("Townsville City", "Jabal us Saraj") count as failures too. On the 2026-09-23 world index this fails 91 of 3,705 checked cases that passed before; they fail on both sides of a comparison, so the relative gate ignores them. Runs from before this check saved no place names. Their answers are not checked for it, and `diff` does not count `wrong_place` against either side when one side has no place names. So a gate run whose base predates the check sees no `wrong_place` change. ResolveRegion passes when one of the regions it returns is an expected one. Both are classed `pass`, `empty`, `wrong_place` (ReverseGeocode only), `wrong_region`, `wrong_country` or `error` (an empty answer is the smaller failure), reported per cohort, and add up to two RPCs per case; a case's ReverseGeocode request is the one that `diff` times. Cases near a border can fail for want of a closer locality; the check gates change, like the others, so only a case that passed on the base and fails on the head counts. `evaluate report --rescore` re-scores them against the current corpus. Connect protobuf answers are decoded into the contract type and must equal the Connect JSON answers field for field. grpcurl runs as a known failure and is reported, not skipped.

`known_failure` labels record triaged baseline failures with their attribution. They stay visible in every report, and a label is only removed after a fix is verified. Do not weaken expectations or regenerate them from a run.

### Redundant parts, stated countries and stated regions

Queries built by joining street, postcode, town, region and country with ", " repeat themselves ("San Francisco, US, United States", "Kyiv, Kyiv, Ukraine", "Madrid, Madrid 28007, ES, Spain") and carry codes that read as another place (IN is Indiana as well as India). 218 cases from seeds in `tests/gold.seeds.jsonl` (tags `redundant_token`, `region_evidence`, `postcode_evidence`, `same_name_elsewhere`, `us_state_zip`) cover this: Wikidata places with the repeated forms as variants, same-name pairs with a stated country (`Delhi, United States` accepts a US Delhi or no answer, never India), and towns placed by a state, region, postcode or district ("Encino, California", "Temple, PA 19560", "La Paz, B.C.S", "Barrow Street, Dublin 4, Irland"). What fixed them:

- A part that repeats another is dropped before parsing (`without_redundant_parts`): the same text, a town beside the same town with its postcode, a country by its code beside its name. A country repeated as the whole query ("Luxembourg, Luxembourg") is tried as written first, since it may name the town of that name. A name written in two scripts is not collapsed.
- A region that only repeats the town ("Tokyo", "Delhi") no longer stands for the country, and a country override needs the answer's own road and house, or a postcode in its country's shape and not the stated one's; a digit or a street in the query is no longer enough.
- A suburb the index files under its town ("Blairgowrie" in Johannesburg) is the town stated when no road narrows it and the region stated fits; a city is not made ambiguous by a village of its name; a street found only because it is named like the stated state is not an answer.
- A name and its region (or, with no region stated, its country) that the parser filed in the wrong fields, a suburb in a "town" that is the province ("Kriel, Mpumalanga"), a town and a state code fused into a road ("Riverside, CT"), still name the candidate (`named_in_region`).
- A written region narrows the town lookup before the top 100 by importance is cut ("Temple, PA"), a three-letter ISO 3166-2 code ("B.C.S") is read as its region, "Dublin 4" is the town Dublin, and a town and postcode that name a place in another country outweigh a coincidence of house and road ("2560 Nidau").
- A postcode the index tags with the stated country but sites in another ("28007" of Spain, placed in Niger) does not veto the stated town. A postcode in a different region does not outweigh the stated town in the stated region when that town is a candidate ("Multan, 66000, Punjab").
- A town the whole parse already split out stays the town when the unsplit street part also contains it ("Kutztown Rd. Temple"). A leading two-letter region code is tried after the place ("NJ, WILLIAMSTOWN").
- The Gaza Strip and the West Bank answer as Palestine: the index has no PS country, and files each as a country of its own.

`us-fl-gainesville` now resolves through the bounded `<country>-<ISO subdivision suffix>-<settlement>` syntax: both codes must exist in the index, the whole settlement name must match an indexed name, and its ancestor chain must contain that subdivision. Unknown subdivisions, contradictory geography and partial settlement names cannot fall through to a looser interpretation. This does not interpret arbitrary producer identifiers. Its verified `known_failure` label is removed. `Flemish` (a demonym) stays empty rather than introducing an open-ended adjective list (`Flemish Region` answers). `stadt oldenburg` and `9e arrondissement de paris` remain labelled failures: they answer with a country (`Stadt Oldenburg, Germany`, `9e arrondissement de paris, france`), and fail only because a bare name answers on an exact name match and these are exact after dropping `stadt` or after the index's own `9th Arrondissement`. Neither is changed here.

Known limits: Atlanta carries the Slovak name "Athens" in the index and outranks Athens-Clarke County, so `Athens, Georgia` answers Atlanta (labelled `known_failure`).

### Registry-first samples

The gold seeds above were picked from Overture, the index's own data, and then checked against a registry, so a registry address the index lacks was never sampled and recall cannot be measured. `tests/registry/` holds samples drawn from the registry first. `evaluate check` and `cargo test` validate each `tests/registry/*.jsonl`; `run --corpus tests/registry/us.jsonl` scores one. They are part of the gold suite: `run --suite gold`, `diff` and `report` read `tests/gold.jsonl`, `tests/registry/*.jsonl`, `tests/gold.landmarks.jsonl` and `tests/gold.suggest.jsonl` unless `--corpus` names a file, `evaluate gold-corpus --out FILE` writes the suite as one file (the eval image carries it as `/app/tests/gold.jsonl`, so the CI run scores both), and the run manifest hashes the files in that order. `diff` compares only case ids both sides have, so the pull request that adds a corpus is not gated on it. Candidate-only cases appear in an **Added cases** table with passed/checked counts and success rates by cohort and RPC; unscored searches are excluded, and SuggestAddress counts each applicable check. Those rates describe the new cases, not a base-to-head improvement or independent-location accuracy. No case is `must_pass`; the known failures are labelled.

Per-country sampling, preparation commands, provenance, limitations and baseline results live in [docs/evaluation/registry/](registry/). Add a country there without editing this guide.

### Gates

`run` fails on a must-pass failure, an untriaged critical result or a transport regression. `diff` fails on any newly failing case, a worse failure class, a new critical result or a must-pass failure in the candidate. It lists newly passing cases for review and drift in unscored cases. SuggestAddress checks do not gate `run`; in `diff` a check that stops passing, or gets a worse class, fails like a search case. Accept a backend change only when both gates pass on the same corpus, consumer, models, reference data and fresh region cache. Report cohort changes as case counts: with about 250 cases, aggregate rates carry several points of uncertainty and per-country rows are individual evidence, not rates.

The `prepare` and `gold` jobs of `.github/workflows/staging-publish.yml` run the gold suite on every pull request that touches the service, its data or the corpus (not on `main` commits, whose images are built only so that a pull request's merge base has one). After the workflow pushes a commit's images, they send the pull request's merge base and head hashes to an authenticated endpoint of a private cluster, which evaluates both staging images on one full index (building it first from the head image's builder when it has none), then runs `evaluate diff --relative` on the two runs and returns the report (failing and worse cases open, the lists to review and the run details folded, a table of each RPC's passing checks on both sides and how many results changed, then a section only for each RPC whose results changed, and a gate line only when it fails; the run's id and step times are in the job summary); the workflow comments it on the pull request (also in the job summary) and keeps the untrimmed report, the run's status and the speed section as the artifact `gold-<head>-<run>-<attempt>` for 90 days, even when the run fails (the endpoint returns only the report, not each case's raw response), sets a `gold-full` commit status, and fails on any newly failing or worse case or new critical result. The report's speed section (SearchAddress, SuggestAddress and ReverseGeocode timings) goes into a comment and a commit status of its own, `gold-speed`, which fails, with an error in the job, when any of the three is more than 10% slower in total, p50, p90 or p99. `--relative` leaves out must-pass cases that fail on both sides, so the check shows change, not accuracy. To reproduce a run locally, use `evaluate run` on each side, then `evaluate diff BASE HEAD --relative`. No pull-request code runs on GitHub in this workflow, and the cluster holds no GitHub credentials. Pull requests by the owner, members and collaborators use the `gold-trusted` environment and run unattended; every other pull request waits in `gold-approval` for a reviewer, who should read the diff first, since approving it runs that author's code in the cluster. Both environments accept workflows from `main` only and hold the endpoint key (`GOLD_GATEWAY_KEY`) and URL (`GOLD_GATEWAY_URL`). While the run is queued or going, the `gold-full` and `gold-speed` comments show it (`queued`, then `running` with the steps seen so far and their times, as the endpoint reports them), so an older commit's report never stands in for this one's; the job polls the endpoint every 10 seconds and edits the comment on each change of step or every 30 seconds; its log has a timestamped line per change, a progress line every 30 seconds and a warning for each poll the endpoint fails to answer (it gives up after 60, 10 minutes). A run that fails or is lost says which step failed and after how long, in the comment, the job summary, an annotation and the commit status: a failed step is a failure of the run, not a verdict on the change. The endpoint reports only the step, not that step's log; giving it a log tail would be the next step, and it lives in the cluster, not here. Pushing again to a pull request, or closing or merging it (`gold-cancel.yml`), cancels its staging build and its run, including the one in the cluster. The workflow skips a commit whose merge base has no multi-architecture staging image (the commit statuses then read "Skipped" and pass), and says so in a comment of its own on the pull request, with the rebase that fixes it; the comment is deleted when a later push can run. The run's progress (queued, running, each step's time, or a failure) is that same status comment, updated in place; the report is posted as the `gold-full` and `gold-speed` comments, and the status comment is deleted after them. A run's start deletes an older commit's report, and a failed run leaves its status comment until the next run. A first index build takes hours and can outlast the job's time limit; the run continues in the cluster and later runs reuse its index.

### Project-local pi gold loop

This repository's `.pi/extensions/gold-wait/` adds `wait_for_gold` and `/gold-loop` to pi only when working in this checkout. Reload pi and approve the project extension if prompted, then run:

```text
/gold-loop https://github.com/Mokto/opengeocoding/pull/181
```

The tool polls every 30 seconds, follows the PR's current head, and waits for both `gold-full` and `gold-speed`. It downloads that head's completed workflow attempt's untrimmed report and saves it in ignored `.pi/reports/gold/`. The default wait is six hours; `wait_for_gold` accepts `timeoutMinutes` up to 720. Cancel the turn to stop waiting. It requires authenticated `gh`; no global extension install or npm dependencies are needed.

The command instructs the agent to review every quality and speed section, reproduce and fix regressions, validate locally, push and wait again. It stops when both quality and measured speed pass or there is a concrete blocker. Missing reports, skipped or unmeasured speed, unavailable artifacts and failed infrastructure never count as success. The tool itself does not edit code, push, retrigger workflows or merge. Changes that do not schedule the gold gate have no gold verdict.

Run its standalone checks with Node.js 22.6+:

```sh
node --experimental-strip-types --test .pi/extensions/gold-wait/gold.test.ts
```

### Address snapshots

`tests/addresses.tsv` holds 1,000 real address and location strings sampled from business addresses, job postings and profile locations. They are spread across 125 countries and stratified by the granularity they target: full address, street, postcode, city, region, country and unparseable. They show how a code or backend change moves everything else; they have no expected answers and measure change, not accuracy. The file holds only the query strings and their geography. Source names, providers, coordinates and identities are removed, and so are imprint addresses and strings naming a company. `tests/snapshots/addresses.tsv` records the accepted behaviour, one row per case: country, level, coordinates (3 decimals, about 100 m), goodMatch, house number, road, postcode, locality, ISO and enriched regions, and the query. A changed answer is one changed row in a PR; `git diff --word-diff` shows just the changed fields. Run metadata (backend version and data date, consumer commit, binary, model and reference-data hashes) is in `addresses.manifest.json` beside it, so it does not clutter the row diff. Full responses stay in the run's `results.jsonl`. Tabs, newlines and other control or separator characters in values are written as backslash escapes.

```sh
target/release/evaluate run --suite addresses --out eval-results/addresses \
  --compare tests/snapshots/addresses.tsv
# after reviewing the changes, accept them
target/release/evaluate snapshot eval-results/addresses tests/snapshots/addresses.tsv
```

`tests/snapshots/gold.nominatim.json` is a reference run of the then 1,280-case gold suite through this service against the Nominatim 5.3.2 deployment it replaces (OSM data of 2026-01-26), taken on 2026-10-13 at 20 requests per second: 888 of 1,280 cases passed (227 of the original 247, 194 of the 286 held out). It holds the run manifest, the class counts and every case's full result except timings and backend traces, one case per line. It is kept for reference and is not regenerated when the gold set changes; compare a run with it using `evaluate diff tests/snapshots/gold.nominatim.json RUN_DIR` (cases added since then show as new). `evaluate snapshot RUN_DIR FILE.json` writes this format.

The diff counts per target granularity which cases gained or lost a result, changed country, became finer or coarser, moved more than 1 km (or less, but visibly in the snapshot), flipped goodMatch, or changed components or regions, and lists each one. `--fail-on-drift` turns any change into a failure. Rerunning an unchanged binary against the same backend produces no drift. A changed answer is not automatically better or worse. Snapshots depend on the backend's data; regenerate the baseline on the target backend before comparing code changes there.

The sampler that queries production data is kept outside this repository; it reuses `opengeocoding::eval` for TSV escaping and hold-out assignment. Other corpora are JSONL in the gold format, or TSV with at least `id` and `query` columns, passed with `--corpus`. Private ones (e.g. replay sets with earlier production geocodes) use the same tooling; keep those and their runs out of this repository.

GitHub-hosted runners have neither a world index nor models, so CI runs only the offline checks in `cargo test`. Run the model-backed suites locally or on a runner with the index and models mounted.
