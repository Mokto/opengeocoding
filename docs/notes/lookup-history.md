# Lookup internals and optimization history

[Implementation notes](README.md) · [Index building](../guides/indexing.md) · [Performance methodology](../performance/README.md)

These records describe different snapshots and workloads, not one current capacity or accuracy result.

## Lookups

Lookups return candidates in the JSON format the resolver reads (Nominatim's search, details and reverse fields); this does not make Nominatim a supported backend. The service renders one search's candidates in English and, when it needs to corroborate a town written in another language, in local names, without searching twice.

It parses with the service's one libpostal parser (serialized), matches places, streets, postcodes and house numbers like Nominatim's all-terms search, and recognizes postcodes from the index when libpostal mislabels them. The resolver uses those repairs for corroboration only when no postcode was parsed, the inferred code does not come from a requested house number, road, unit, floor or P.O. box, and reparsing preserves the primary house number and road without duplicate labels. Stated country and region fields remain constraints. A Dutch house address with a separately comma-delimited country also rejoins postcode letters mislabelled as a second country (`1234 TJ Town, Netherlands`): the letters must immediately follow the parsed postcode digits in the same comma part, form a full Dutch postcode, and leave a town name. Separate country parts, additional country labels, stated administrative regions and non-Dutch countries are not repaired this way. A separately comma-delimited state is not rewritten as a town. It reads Japanese block addresses (`東京都港区芝公園4-2-8` is chōme 4 of 芝公園, block 2, house 8) and Chinese road addresses itself, since libpostal splits them. Native Korean road-name and land-lot addresses use exact indexed numbers and an ordered province/city/district/township hierarchy; missing houses may answer the named locality with `goodMatch` false, never an invented road/lot-number conversion. Korean suggestions use the same hierarchy, including while a road or number is unfinished; see [the Korean evaluation notes](../evaluation/registry/kr.md) for coverage and remaining failures. Streets are looked up in the named town, then a same-named county, then a same-named city-province (Istanbul), then by postcode and near the postcode's centre. It reports each house's own postcode, as the source data gives it. It remains experimental (`ReverseGeocode` reads houses and streets and `ResolveRegion` simplified polygons, see [Reverse geocoding](../guides/api.md#reverse-geocoding)). It reads importance through cached per-segment fast-field columns and checks exact names against hashes folded at startup; Tantivy's `order_by_fast_field` reopened every segment's column per query and cost more than the search itself. The 12 GB index (Tantivy, house-number FSTs and `places.tsv`) is memory-mapped; in an earlier measurement 1.3 GB of it was resident after 20 seconds of load. On an 18-core laptop shared with other work (load average about 13), the service answered the 1,000 address samples at about 360 requests per second over one connection and 1,600 to 2,100 over eight (p99 39 ms). The same build calling a separate `serve_index` process over HTTP, on the same index, answered about 220 and 940 to 1,290 (p99 63 ms), with identical responses. The service's memory footprint was 3.5 GB, against 6.0 GB for the two processes, which each loaded libpostal's models. Per gold query it searched the index 1.8 times on average, where the HTTP version made 3.2 calls: one search now serves both languages. These are single measurements on one machine, not capacity guarantees.

A later round of changes was measured on an 11 GB world index, with 808 sample queries over one connection and over 16, alternating the old service on the index as built (319 segments) with the new one on a copy merged to four segments, on a busy 18-core laptop. Responses were identical. With the parse cache off: 170 to 806 requests per second over one connection (p95 21.9 to 3.9 ms), 1,516 to 5,512 over 16, and 8.2 to 1.4 ms of CPU per request. Three changes account for it, in order of size: merging the segments (CPU 8.2 to 3.0 ms; the merge happens in the builder, so this needs a rebuilt index), filtering a lookup's document kind in the collector (3.0 to 1.4 ms: a `kind:s` term has 40 million postings that Tantivy walked block by block for every street lookup, which took one name from 0.007 ms to 0.7 ms; the kind is read from which fast columns a document has, so existing indexes gain from it too), and running a request on one blocking thread instead of one hop per parse and search. The same comparison between the two release images in Linux containers (cache off, index bind-mounted from the host) gave 109 to 599 requests per second over one connection (p95 33.5 to 5.3 ms) and 957 to 2,850 over 16, with resident memory 5.0 GiB before and 4.2 GiB after. With the default parse cache the same run on the host gave 875 and 8,724 requests per second, but the 808 queries repeat there, so that number flatters real traffic; within one request alone the cache saved 0.6 of about 2.3 libpostal parses. Startup with the world index dropped from 5.9 to 2.7 seconds (models load while the place table is read, and the table is parsed on all cores). A country filter in the collector measured no gain, and mimalloc gained 1% to 3% throughput for 0.75 GB more memory, so neither was kept. These are single measurements, not capacity guarantees.

A third round changed only how lookups run, not what they return. A lookup seeks the document runs of its kind (the builder writes places, streets and postcodes in 10 to 20 runs per segment), so a place's name no longer walks the millions of streets that share its words. The country filter reads a per-document country table built at startup (2 bytes a document, about 0.1 GB for a world index) instead of intersecting with a country term, whose postings tantivy's skip list walks one block at a time. A request remembers its own lookups (over half of them were repeats: the same town for every fallback and street scope), existence checks stop at the first match, and a place's English name is located once at startup. On the same busy laptop and world index, with the parse cache off, the 1,000 address samples took a mean of 0.8 ms instead of 2.4 ms over one connection (p99 5.3 ms instead of 23 ms; 1,240 requests per second instead of 410) and 5,000 to 5,400 requests per second over 16 instead of 3,100 to 3,300, where libpostal's single lock now sets the limit. With the parse cache on and the samples repeating, 16 connections gave 16,000 requests per second instead of 4,400. The gold suite's 3,732 cases returned identical responses, with total SearchAddress time down 63% (p99 31.5 to 10.7 ms), and `tests/suggest.rs` typed prefixes again took p50 82 µs instead of 125 µs (p99 3.4 ms instead of 4.6 ms). These are single measurements, not capacity guarantees.

A fourth round changed the index, not what lookups return. Tantivy walks a word's skip list one block at a time, so a lookup holding a common word ("st", "rue", "2") read about all of that word's postings, in every country, even when the lookup named one. The builder now also indexes each place's and street's name words, and each street's postal-city words, behind the document's country (`cnames`, `ccity`; they replace `ctok`, which no lookup read), and a lookup that names a country reads those. The index is one segment instead of four, its documents in kind order (places, postcodes, then streets), and each lookup starts with its kind's span of documents: a place's words that name no place no longer send the intersection through every street before the collector sees the kind. A union of up to 16 terms (a scope of places) seeks each term instead of tantivy's union, which filled a window of 4,096 documents from every term on each seek: a suggestion for "United States", whose scope held the country's 10 million streets, took 2 ms instead of 12 ms. On the gold suite's 42,138 cases on a world index, main's index and service and this index and service returned the same results; on an 18-core laptop shared with other work, the gold speed sample (the fastest of three requests per case, parse cache off) took 22% less time for SearchAddress (p90 26% less) and 37% less for SuggestAddress (p90 48% less), and ReverseGeocode, which reads none of these lookups, was unchanged. Lookups that name no country still read every country's postings. These are single measurements on one machine, not capacity guarantees.

In one run against the October 2026 Overture release with the OSM, OpenAddresses and GeoNames [source inputs](../guides/indexing.md#overture-address-index), the gold suite passed 1,038 of its first 1,280 cases (231 of the 286 held out), against 992 for the index before the October 13 data and parsing work. On the 2,875-case version it passed 2,136 (433 of the 582 held out), including 545 of the 926 damaged addresses: a typo in the street (2 of 95) and a wrong postcode (10 of 95) were its weakest kinds, since streets then matched only on exact (canonicalized) words. Lookups now correct a street with one misspelt word (within one edit, same first letter, or a misspelt street type) when a resolved town or postcode holds a street with the other words and the house number. The service accepts a candidate whose postcode disagrees with the requested one when its house number, road and town all agree, after every candidate holding the postcode has been refused, and returns it with goodMatch false. When the postcode identifies another part of that street in the same locality, it instead falls back to postcode or locality level rather than choosing a contradictory house. Existing nearby-source postcode corroboration and shared postcode-area compatibility still apply. With both, and 32 Census expectations corrected (their five-digit house numbers had been read as postcodes), the 2,875 cases passed 2,308 (459 of the 582 held out), including 701 of the 926 damaged addresses: 82 of 95 street typos and 73 of 95 wrong postcodes. One must-pass case regressed with them: "10 Rue de Rivoli, 75001 Paris, France" answered number 10 of the same street in 75004. The same-street postcode conflict guard now makes it fall back to postcode 75001 without a house, resolving that failure without changing its expectation. Of the original 247 cases it passed 239; Nominatim 5.3.2 with January 2026 OSM data passed 227, and the only case Nominatim passed and the index did not is a Dubai boulevard whose street data names a smaller locality than Dubai. Of the 405 address cases (Wikidata landmarks in 90 countries and registry addresses from France, the Netherlands, the United States, Norway, Switzerland and Spain), it passed 286. Most remaining failures are data gaps (streets or villages missing in OSM-only countries) or the service rejecting the index's right first answer on libpostal's parse ("Addis Ababa, Ethiopia" parses as one city name); those critical ones are labelled in `tests/gold.seeds.jsonl`. On the 1,000 address samples, the index answered 827 (Nominatim 855) and 143 at house level (117). Where the sample's country is known, it chose the right country for 97.3% of its answers (Nominatim 97.5%) and claimed a good match in the wrong country 14 times (Nominatim 14). To keep wrong countries down, a lookup answers a street with nothing to place it only when at most three same-named streets with that number exist, all in one country. It answers a place name without a country only on an exact name match, and a bare postcode without a country only when one country uses it. These are single runs on curated and sampled inputs, not production accuracy.
